# 05. 설계 결정 기록 (ADR)

> 보존 문서: FinMATE 당시의 설계·검증 기록입니다. 현재 제품 방향은 [제품 비전](../product/vision.md), 현행 요구사항은 [문서 안내](../README.md)를 따릅니다. 본문의 완료 표시는 이번 정리 작업에서 재검증한 결과가 아닙니다. 코드 링크의 organization 저장소와 `main` 경로는 분리 후 목적지이며 원격 반영은 별도 확인이 필요합니다.
각 결정은 "결정 / 이유 / 대안"의 형식으로 남긴다. 새 결정은 파일 맨 아래에 追加한다.

## ADR-001: 실제 매매·계좌 연동 기능을 제외함

- 결정: 실제 증권계좌 연동, 매수/매도 주문 기능은 구현하지 않는다.
- 이유:
  - 3일 과제 범위를 초과한다.
  - "투자 자문/주문"으로 오인될 경우 금융 규제 이슈가 생길 수 있다.
  - 본 과제의 평가 핵심은 AI 분석 로직의 설계와 웹 서비스의 UI-데이터-API 일관성이지, 실제 거래 기능이 아니다.
- 대안: 2차에서 가상 포트폴리오 저장 기능(FR-09)으로 "관심 상품 담아두기" 경험만 제공한다.

## ADR-002: "투자 추천"이 아닌 "탐색/근거 제공"으로 표현

- 결정: 서비스 문구와 API 응답에서 "추천"보다 "탐색", "적합도 안내"라는 표현을 우선 사용한다.
- 이유: 실제 자산 배분 조언처럼 보이면 범위가 과도하게 커지고(PDF 평가 기준 "과도하게 큰 범위" 감점 요인), 금융상품 판매·자문으로 오해될 수 있다.
- 대안: `category_recommendations.reason` 필드에 "판단 근거"를 담아 설명 가능성을 강조하되, 보장성 문구는 넣지 않는다.

## ADR-003: 관리자 회원가입 화면은 MVP에서 생략

- 결정: 관리자는 로그인 없이 시드 데이터로 가정하고, 관리자 회원가입/로그인 API는 P1로 분류한다.
- 이유: 회의실 예약 서비스 예시처럼 관리자 인증 플로우를 넣으면 화면 수가 늘어나 3일 내 완성이 어려워진다. 평가 배점(목표 시스템 정의 30점)의 핵심은 일반 사용자의 AI 분석 흐름이다.
- 대안: 필요 시 2차 Agile에서 관리자 로그인 화면(S0)과 `admin-auth` API 태그를 추가한다.

## ADR-004: AI 분석은 "자연어 자유 입력"이 아닌 "선택형 질문 응답" 기반으로 시작

- 결정: MVP에서는 사용자가 자연어로 자유롭게 입력하는 방식 대신, 사전 정의된 선택형 질문(questions/question_choices)에 답하는 방식으로 성향을 분석한다.
- 이유: 자연어 자유 입력은 파싱/추출 로직이 복잡해 3일 내 안정적으로 구현·검증하기 어렵다. 선택형 응답이라도 "AI가 조합을 해석해 근거를 설명"하는 부분(investment_profiles.reasoning)은 그대로 유지되어 AI 서비스성을 잃지 않는다.
- 대안: 2차 Agile에서 자연어 입력을 answers 위에 추가 레이어로 확장한다.

## ADR-005: 1차 Agile은 진단부터 상품 탐색까지의 P0 세로 슬라이스로 고정

- 결정: 1차 산출물은 회원가입/로그인 → 선택형 진단 → AI 결과·근거 → 추천 카테고리·예시 상품 탐색(S1~S6)까지만 다룬다.
- 이유: 과제 평가의 핵심 흐름을 짧고 검증 가능하게 만들고, 비교·포트폴리오·관리자 기능으로 인한 문서와 구현의 분산을 막는다.
- 대안: 모든 기능을 1차에 설계하는 방식은 2차 확장 후보와 현재 완료 기준을 혼동시키므로 채택하지 않는다.

## ADR-006: AI는 개별 상품이 아닌 카테고리를 우선 안내

- 결정: 분석 결과는 투자 성향, 판단 근거, 탐색 카테고리 ID·순위·이유를 반환한다. 개별 상품은 해당 카테고리의 사전 등록 목록에서 탐색한다.
- 이유: 상품 단위의 개인 맞춤 자문처럼 보이는 위험을 낮추고, 추천 근거와 데이터 모델을 단순하게 일치시킨다.
- 대안: AI가 상품별 추천 사유까지 직접 생성하는 방식은 2차에서 별도 검토한다.

## ADR-007: 1차 분석 API는 동기 응답으로 단순화

- 결정: `POST /assessments`는 규칙 판정과 설명 생성을 한 요청에서 완료하고 201을 반환한다. LLM 설명 생성 실패는 템플릿으로 대체하며, 문항·카테고리 데이터 준비 실패만 503으로 반환한다.
- 이유: 핵심 결과의 가용성을 LLM 외부 의존성에 묶지 않으면서도 3일 설계 과제에서 큐·폴링·웹훅을 추가하지 않는다.
- 대안: 분석 시간이 길어지거나 재시도·상태 추적이 필요해지면 2차에서 202 응답과 상태 폴링으로 확장한다.

## ADR-008: LLM은 설명 생성기로만 사용하고 실패 시 템플릿으로 대체

- 결정: 점수·성향 등급·탐색 카테고리는 규칙 엔진이 결정한다. LLM은 실제 답변을 근거로 한 설명 문장만 생성하며, 호출 실패·키 부재 시 `reasoningSource=TEMPLATE`로 저장한다.
- 이유: 금융 관련 결과의 재현성과 통제 가능성을 확보하고, 외부 모델 장애가 핵심 흐름을 중단시키지 않도록 한다.
- 대안: LLM이 성향과 상품을 직접 결정하는 방식은 설명 가능성·검증 가능성이 낮아 MVP에서 채택하지 않는다.

## ADR-009: MVP 인증은 메모리 토큰 저장소로 한정

- 결정: MVP 데모에서는 로그인 시 발급한 opaque token을 프로세스 메모리에 보관한다. 서버 재시작 시 토큰이 만료되며, 토큰 만료·로그아웃·다중 인스턴스 공유는 제공하지 않는다.
- 이유: 과제의 핵심은 진단 세로 슬라이스이고, 별도 인증 인프라 없이 사용자 소유권 검증을 보여주기 위함이다.
- 대안: 실제 서비스화 전에는 만료·폐기·재발급 정책과 공유 세션 저장소 또는 검증 가능한 토큰 체계를 도입한다.

## ADR-010: 등급 비교는 실제 적합성 판단이 아닌 내부 탐색 필터

- 결정: 5단계 성향과 1~6 카테고리 위험등급의 비교식은 과제용 예시 데이터를 탐색하기 위한 내부 규칙으로만 사용한다. 화면과 API에서는 `투자 권유 가능`, `적합성 판단` 대신 `탐색 기준`, `안내 범위`로 표현한다.
- 이유: 단순화한 비교식이 실제 금융기관의 상품별 위험정보·고객 정보·법적 절차를 대체하지 않으며, 사용자에게 투자 자문으로 오해될 수 있기 때문이다.
- 대안: 실제 서비스화 시 상품별 공식 위험정보, 투자자 정보 확인, 적합성·적정성·설명의무 등 별도 준법 설계와 검토를 거친다.

## ADR-011: P0 예시 상품은 카테고리 위험등급과 일치

- 결정: P0에서는 상품과 소속 카테고리의 `risk_grade`를 동일하게 유지하고, 시작 시 시드 데이터 불변식을 검증한다.
- 이유: 두 필드를 모두 노출하면서 서로 다른 등급을 허용하면 추천 필터와 상품 상세가 모순될 수 있다.
- 대안: P1에서 상품별 위험등급을 독립적으로 운영할 경우 카테고리 필터와 상품 필터의 우선순위·불일치 처리 규칙을 별도로 정의한다.

## ADR-012: 주식 용어 사전은 JSON 시드 + DB 운영 구조로 둔다

- 결정: 247개 용어의 원본은 분류별 JSON(`glossary/terms/*.json`)으로 관리하고, 기동 시 DB에 **없는 slug만** 넣는다. 이후 수정은 관리자 화면의 초안 → 검증 → 게시로만 한다.
- 이유: 콘텐츠 개정 이력을 코드 리뷰로 남기면서도, 세율·제도 변경처럼 급한 수정은 배포 없이 반영해야 한다. 시드를 매번 덮어쓰면 운영자 수정이 사라진다.
- 대안: 전부 DB에서만 관리하면 초기 콘텐츠의 리뷰·출처 검증이 어렵고, 전부 JSON이면 운영 중 수정이 불가능하다.

## ADR-013: 모델 학습은 Python 표준 라이브러리, 서빙은 Java가 같은 계산으로 수행한다

- 결정: `ml/train.py`가 외부 패키지 없이 학습·평가하고 JSON 산출물을 내보낸다. Spring Boot는 같은 정규화·n그램·가중치 계산을 Java로 구현하며, Python이 저장한 정답 예측과 문장·질문 단위로 일치하는지(`MlParityTest`) 검사한다.
- 이유: 배포 단위를 하나(Java)로 유지하고, 사용자 요청마다 Python 프로세스를 호출하는 지연·장애 지점을 없앤다. 표준 라이브러리만 쓰면 누구나 같은 결과를 재현할 수 있다.
- 대안: Python 추론 서버를 따로 띄우는 방식은 운영 부담이 늘고, ONNX 등은 이 규모의 선형 모델에 과하다. 두 구현의 드리프트 위험은 일치 테스트로 상쇄한다.

## ADR-014: 자유 서술 신호는 등급을 바꾸지 않고 원문을 저장하지 않는다

- 결정: 진단 마지막의 자유 서술은 선택 입력이다. 규칙 엔진이 등급을 확정한 뒤 모델이 성향·태그를 추정하고, 설문과 2단계 이상 차이 나며 확신도 0.5 이상일 때만 `NARRATIVE_MISMATCH` 확인 플래그를 붙인다. 원문은 버리고 추정 결과만 스냅샷에 남긴다.
- 이유: 등급의 재현성·통제 가능성(ADR-008)을 지키면서, 보기만으로 표현되지 않은 생각을 "다시 확인할 신호"와 "학습 추천"으로 활용한다. 원문은 민감한 재무 상황을 담을 수 있어 최소 수집 원칙을 따른다.
- 대안: 서술로 등급을 보정하는 방식은 같은 답변에 다른 등급을 만들 수 있고 적합성 판단처럼 읽힐 위험이 있어 채택하지 않는다.

## ADR-015: 성향 모델은 생성 코퍼스로 학습하고 사람이 쓴 보류셋으로만 평가한다

- 결정: 설문 축(목적·손실 반응·기간·경험·여력)으로 만든 문장 조각을 조합해 라벨 균형 학습 문장을 만들고, 라벨은 실제로 뽑힌 조각 점수의 가중 평균으로 정한다. 평가는 생성기와 별도로 사람이 쓴 보류 문장(115개)과 주제 무관 문장(20개)으로만 한다.
- 이유: 실제 사용자 문장을 모을 수 없는 상황에서 40문장 학습(v1)은 새 표현에 약했다(보류 정확도 0.52). 생성 코퍼스는 표현 범위를 넓히고, 분리된 보류셋은 "생성기를 외웠는지"를 드러낸다.
- 대안: 보류 문장을 학습에 섞으면 숫자는 좋아지지만 일반화 성능을 알 수 없게 된다. 보류 문장과 비슷해진 생성 조각은 조각 쪽을 수정하고 누수 지표를 테스트로 감시한다.

## ADR-016: 용어 검색 인덱스는 DB의 공개 용어로 만들고 게시 이벤트로 재구성한다

- 결정: 모델 파일에는 IDF·필드 가중치·가산점만 담고, 문서 벡터는 서버가 공개 용어로 만든다. 게시·공개 내리기·시드 적재 시 `GlossaryContentChangedEvent`를 커밋 후에 받아 인덱스를 버리고 다음 검색에서 다시 만든다.
- 이유: 관리자 수정이 재학습·재배포 없이 바로 검색에 반영되어야 한다. 커밋 전에 버리면 다른 요청이 옛 내용으로 인덱스를 다시 만들 수 있다.
- 대안: 학습 시점 문서를 고정하면 비공개 처리한 용어가 검색에 남는 등 콘텐츠와 검색이 어긋난다.

## ADR-017: 로그인 세션을 DB에 해시로 저장한다 (ADR-009 대체)

- 결정: 32바이트 난수 토큰을 발급하고 SHA-256 해시만 `auth_sessions`에 저장한다. 기본 30일 만료, `POST /auth/logout`으로 폐기, `GET /auth/me`로 확인한다. 관리자 역할은 서버 환경변수로만 만든다.
- 이유: 메모리 저장소는 재시작·다중 인스턴스에서 세션이 사라지고 로그아웃이 불가능했다. 해시만 저장하면 DB가 유출돼도 토큰을 쓸 수 없다.
- 대안: JWT는 즉시 폐기가 어렵고, 이 서비스 규모에서는 서버 저장 세션이 단순하다.

## ADR-018: 학습·용어·모의투자·모델 실험실은 로그인 없이 연다

- 결정: 진단·이력·내 학습·관리 화면만 로그인을 요구하고, 학습 콘텐츠와 모델 실험은 누구나 쓴다. 로그인 상태에서 푼 문제만 진도·오답노트에 저장한다. 보호 화면에서 로그인하면 원래 화면으로 돌아온다.
- 이유: docs/09 "재진단 제한·등급과 무관하게 학습은 열려 있어야 한다"를 화면 라우팅에서도 지킨다. 기존 라우터가 학습 화면을 막고 있던 모순을 해소했다.
- 대안: 전부 로그인 뒤에 두면 첫 방문자가 가치를 경험하기 전에 이탈한다.

## ADR-019: 학습 개념·확인 문제도 JSON 시드 + DB 운영 구조로 두고, 게시 직전에 트리 전체를 다시 검증한다

- 결정: `learning/concepts.json`은 시드로만 쓴다. 기동 시 `learning_concepts`·`learning_quiz_items`에 **없는 개념만** 넣고, 이미 있는 개념의 문항은 건드리지 않는다. 관리자는 개념 본문과 확인 문제를 한 초안(`learning_concept_drafts`)으로 저장하고, 게시할 때 "게시하면 공개될 트리"를 시드와 같은 규칙(`LearningTree`: 부모·레벨 일치, 정답 정확히 1개, 선택지 3개 이상, 모든 선택지 해설, 출처, 문항 id 중복 금지)으로 다시 만들어 본 뒤 반영한다. 게시·공개 내림은 당시 본문·문항 전체와 함께 `learning_concept_revisions`에 불변 기록하고, 커밋 후 `LearningContentChangedEvent`로 학습 카탈로그 캐시를 버린다. 학습 콘텐츠 버전은 시드 버전 + 공개 개념 (slug, 개념 버전) 집합의 해시라 게시하면 바뀌고, 옛 버전으로 제출한 확인 문제는 409가 된다.
- 이유: 해설 오류 같은 급한 수정을 배포 없이 고쳐야 한다(FR-18). 개념은 용어와 달리 트리라서 한 개념의 레벨·상위 개념 수정이나 공개 내림이 다른 개념의 규칙을 깰 수 있다. 개념 하나만 보는 검증으로는 막을 수 없으므로 게시 직전에 전체를 검증하고, 두 관리자의 동시 게시가 서로의 검증을 건너뛰지 않도록 개념 행 전체를 slug 순서로 잠근다. 선택지는 순서가 곧 choice ID(`{문항 id}-choice-{순번}`)라 문항 행에 JSON 배열로 함께 저장해 순서와 정답 개수가 어긋난 채 저장될 틈을 없앤다. 하위 개념이 공개 중이면 상위 개념의 공개를 내릴 수 없고, 연결 개념이 비공개가 된 용어는 상세에서 개념 링크를 비운다.
- 대안: 매 요청 DB에서 트리를 읽으면 트리 응답 한 번에 개념 수만큼 조회가 늘고, 시간 기반 캐시(TTL)는 게시 직후 잠시 옛 해설과 새 버전이 섞일 수 있다. 개념 추가·삭제, 여러 서버 인스턴스 사이의 캐시 무효화는 이번 범위에서 뺐다. 인스턴스를 늘릴 때는 콘텐츠 버전 행을 두고 요청 시 비교하거나 메시지로 무효화를 전파한다.
