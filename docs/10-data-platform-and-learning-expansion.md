# 10. 실데이터·상품 학습 플랫폼 고도화 설계

## 목표

FinMATE를 단순한 상품 목록이 아니라, **상품 구조를 학습하고 근거가 있는 과거 자료를 탐색하며 현재 데이터와 구분해서 보는 학습형 금융 정보 플랫폼**으로 확장한다.

## 수집 방식 결정

| 데이터 | 우선 방식 | 이유 | 주기 |
|---|---|---|---|
| 기업 공시·재무 | OpenDART API | 공식 식별자와 공시 원문을 제공 | 공시 이벤트 + 일배치 |
| 거래소 시세·종목 | KRX 공식 데이터 계약/API | 시세 정확성·라이선스 관리 | 장중 또는 지연 시세 |
| 펀드·ETF 기준정보 | 금융기관/공식 상품 파일·계약 API | 수수료·위험등급·설명서 확인 | 일배치 |
| 교육 자료 | 공식 문서·공개 PDF의 허용된 수집 | 개념 설명과 출처 보존 | 수동 검수 + 변경 감지 |
| 뉴스·웹페이지 | 크롤링은 보조 수단 | robots.txt·약관·저작권·변경 안정성 위험 | 허용된 사이트만 |

크롤링과 스크래핑을 먼저 시작하지 않는다. 공식 API 또는 라이선스 데이터가 있으면 그것을 우선한다. 웹 수집은 사이트별 허용 범위, 호출 제한, 원문 보존, 삭제·수정 반영 정책을 확인한 뒤 어댑터로 격리한다.

## 저장 구조

운영 DB에는 현재값과 원문·이력을 분리한다.

- `source_registry`: 공급자, 이용약관, 호출 제한, 마지막 성공 시각
- `source_documents`: 원문 URL, 수집 시각, content hash, 원문 저장 위치, 삭제·수정 상태
- `instrument_master`: ISIN/종목코드/상품코드 중심의 표준 상품
- `instrument_snapshots`: 기준일별 가격·NAV·위험·보수·유동성 지표
- `disclosures`: 공시 문서와 보고기간, 원문 문서 연결
- `concepts`: 위험, 수수료, 듀레이션, NAV, 스프레드 등 개념
- `content_revisions`: 개념 설명, 차트 설정, 대상 상품, 근거 문서, 검수자, 공개 상태
- `learning_progress`: 사용자의 학습 완료·퀴즈 결과

현재 상품 테이블을 직접 덮어쓰지 않고 snapshot을 추가한다. 그러면 “현재 상품”과 “2024년 당시 자료”를 함께 제공할 수 있다.

## 과거 자료 탭

가능하다. 자료의 `published_at`, `effective_from`, `effective_to`, `observed_at`을 분리해 `과거 자료` 탭을 제공한다. 과거 문서는 현재 위험등급으로 재분류하지 않고, 당시 원문과 당시 데이터로 보여준다. 현재값과 과거값을 비교할 때는 변경된 필드와 출처를 함께 표시한다.

## 학습 콘텐츠 구조

각 상품군을 다음 5단계로 구성한다.

1. 한 문장 개념
2. 구조 그림: 돈의 흐름, 위험의 발생 지점, 현금화 경로
3. 실제 데이터 읽기: 가격·NAV·보수·거래량·듀레이션 등
4. 과거 사례: 특정 시점의 공시·가격·설명서
5. 확인 퀴즈와 “이 상품에서 확인할 문서” 체크리스트

초기 콘텐츠 상품군은 주식, 채권, 펀드, ETF, MMF, 예금·현금성, ELS/구조화상품, 리츠, 연금상품, 파생·레버리지로 확장한다. 각 상품군에서 위험, 수익, 유동성, 비용, 분산, 세금, 복잡도를 공통 개념으로 연결한다.

## API 규모 예상

최종 배포형 기준 예상은 **약 43~56개**다.

| 영역 | 예상 수 |
|---|---:|
| 인증·동의·개인정보 | 6~8 |
| 진단·재진단·이력·근거 | 9~12 |
| 상품·검색·비교·관심목록 | 8~10 |
| 학습 개념·콘텐츠·퀴즈·진도 | 8~11 |
| 과거 자료·공시·차트 | 5~7 |
| 관리자·수집 작업·검수 | 7~8 |
| **합계** | **43~56** |

현재 발표용 구현에서 먼저 필요한 API는 `GET /learning/concepts`, `GET /learning/concepts/{slug}`, `GET /assessments/availability`, `GET /assessments`, 기존 상품·진단 API를 포함해 약 20개 안팎이다. 실데이터 수집과 관리자 검수 API는 배포 단계에서 추가한다.

## 배포 단계 파이프라인

`수집 스케줄러 → 원문 저장 → hash/idempotency 검사 → 정규화 → 품질검사 → snapshot 저장 → 개념/상품 연결 → 검수 → 공개 API` 순서로 운영한다. 수집 실패는 기존 정상 데이터를 덮어쓰지 않고 실패 큐와 모니터링에 남긴다.

## Self-Consistency 검토

세 가지 설계를 비교했다.

- 전면 웹스크래핑: 빠르게 시작할 수 있지만 데이터 권리·변경 감지·재현성이 약하다.
- 외부 API만 사용: 숫자 데이터에는 강하지만 설명서·과거 문서·학습 자료가 부족하다.
- **API 우선 + 원문/스냅샷 저장 + 허용된 문서 수집(채택)**: 정확성, 과거 재현성, 학습 콘텐츠 확장을 함께 만족한다.

따라서 현재 구현은 공급자 인터페이스와 출처 연결을 먼저 두고, 실제 키·계약이 필요한 수집기는 별도 어댑터로 추가하는 구조를 채택했다.

## Self-Reflection

현재 구현은 아직 실시간 투자 데이터의 운영 수준 완성품이 아니다. OpenDART·KRX의 인증키, 이용계약, 호출 한도, 상품별 공식 데이터 계약이 필요하고, 가격 데이터는 지연 시세인지 실시간 시세인지 화면에 표시해야 한다. 또한 콘텐츠는 교육용 요약이므로 법률·세무 자문이나 상품 적합성 판단으로 확장하지 않는다.

다음 구현 순서는 `PostgreSQL + Flyway 스키마 → OpenDART adapter → 상품 마스터/스냅샷 → 관리자 검수 → 차트·과거 탭 → KRX/상품 데이터 계약`이다.

## 구현된 첫 단계

현재 코드에는 `LearningCatalog`와 `/learning/concepts` API, 출처 연결 도식 UI, `MarketDataProvider` 공급자 경계, OpenDART 호출 어댑터의 최소 골격을 추가했다. API 키가 없는 발표 환경에서는 기존 학습 카탈로그가 동작하며, 배포 환경에서 `OPENDART_API_KEY`를 주입한 수집 작업만 활성화하면 된다. 다음 단계에서 수집 응답을 `source_documents`에 먼저 저장하고, 재시도·중복 hash·정규화·스냅샷 저장을 순서대로 연결한다.
