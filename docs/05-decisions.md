# 05. 설계 결정 기록 (ADR)

각 결정은 "결정 / 이유 / 대안"의 형식으로 남긴다. 새 결정은 파일 맨 아래에 追加한다.

## ADR-001: 실제 매매·계좌 연동 기능을 제외함

- 결정: 실제 증권계좌 연동, 매수/매도 주문 기능은 구현하지 않는다.
- 이유:
  - 3일 과제 범위를 초과한다.
  - "투자 자문/주문"으로 오인될 경우 금융 규제 이슈가 생길 수 있다.
  - 본 과제의 평가 핵심은 AI 분석 로직의 설계와 웹 서비스의 UI-데이터-API 일관성이지, 실제 거래 기능이 아니다.
- 대안: 2차에서 가상 포트폴리오 저장 기능(FR-09)으로 "관심 상품 담아두기" 경험만 제공한다.

## ADR-002: "투자 추천"이 아닌 "탐색/근거 제공"으로 표현

- 결정: 서비스 문구와 API 응답에서 "추천"보다 "탐색", "적합도 안내"라는 표현을 우선 사용한다.
- 이유: 실제 자산 배분 조언처럼 보이면 범위가 과도하게 커지고(PDF 평가 기준 "과도하게 큰 범위" 감점 요인), 금융상품 판매·자문으로 오해될 수 있다.
- 대안: `category_recommendations.reason` 필드에 "판단 근거"를 담아 설명 가능성을 강조하되, 보장성 문구는 넣지 않는다.

## ADR-003: 관리자 회원가입 화면은 MVP에서 생략

- 결정: 관리자는 로그인 없이 시드 데이터로 가정하고, 관리자 회원가입/로그인 API는 P1로 분류한다.
- 이유: 회의실 예약 서비스 예시처럼 관리자 인증 플로우를 넣으면 화면 수가 늘어나 3일 내 완성이 어려워진다. 평가 배점(목표 시스템 정의 30점)의 핵심은 일반 사용자의 AI 분석 흐름이다.
- 대안: 필요 시 2차 Agile에서 관리자 로그인 화면(S0)과 `admin-auth` API 태그를 추가한다.

## ADR-004: AI 분석은 "자연어 자유 입력"이 아닌 "선택형 질문 응답" 기반으로 시작

- 결정: MVP에서는 사용자가 자연어로 자유롭게 입력하는 방식 대신, 사전 정의된 선택형 질문(questions/question_choices)에 답하는 방식으로 성향을 분석한다.
- 이유: 자연어 자유 입력은 파싱/추출 로직이 복잡해 3일 내 안정적으로 구현·검증하기 어렵다. 선택형 응답이라도 "AI가 조합을 해석해 근거를 설명"하는 부분(investment_profiles.reasoning)은 그대로 유지되어 AI 서비스성을 잃지 않는다.
- 대안: 2차 Agile에서 자연어 입력을 answers 위에 추가 레이어로 확장한다.

## ADR-005: 1차 Agile은 진단부터 상품 탐색까지의 P0 세로 슬라이스로 고정

- 결정: 1차 산출물은 회원가입/로그인 → 선택형 진단 → AI 결과·근거 → 추천 카테고리·예시 상품 탐색(S1~S6)까지만 다룬다.
- 이유: 과제 평가의 핵심 흐름을 짧고 검증 가능하게 만들고, 비교·포트폴리오·관리자 기능으로 인한 문서와 구현의 분산을 막는다.
- 대안: 모든 기능을 1차에 설계하는 방식은 2차 확장 후보와 현재 완료 기준을 혼동시키므로 채택하지 않는다.

## ADR-006: AI는 개별 상품이 아닌 카테고리를 우선 안내

- 결정: 분석 결과는 투자 성향, 판단 근거, 탐색 카테고리 ID·순위·이유를 반환한다. 개별 상품은 해당 카테고리의 사전 등록 목록에서 탐색한다.
- 이유: 상품 단위의 개인 맞춤 자문처럼 보이는 위험을 낮추고, 추천 근거와 데이터 모델을 단순하게 일치시킨다.
- 대안: AI가 상품별 추천 사유까지 직접 생성하는 방식은 2차에서 별도 검토한다.

## ADR-007: 1차 분석 API는 동기 응답으로 단순화

- 결정: `POST /assessments`는 규칙 판정과 설명 생성을 한 요청에서 완료하고 201을 반환한다. LLM 설명 생성 실패는 템플릿으로 대체하며, 문항·카테고리 데이터 준비 실패만 503으로 반환한다.
- 이유: 핵심 결과의 가용성을 LLM 외부 의존성에 묶지 않으면서도 3일 설계 과제에서 큐·폴링·웹훅을 추가하지 않는다.
- 대안: 분석 시간이 길어지거나 재시도·상태 추적이 필요해지면 2차에서 202 응답과 상태 폴링으로 확장한다.

## ADR-008: LLM은 설명 생성기로만 사용하고 실패 시 템플릿으로 대체

- 결정: 점수·성향 등급·탐색 카테고리는 규칙 엔진이 결정한다. LLM은 실제 답변을 근거로 한 설명 문장만 생성하며, 호출 실패·키 부재 시 `reasoningSource=TEMPLATE`로 저장한다.
- 이유: 금융 관련 결과의 재현성과 통제 가능성을 확보하고, 외부 모델 장애가 핵심 흐름을 중단시키지 않도록 한다.
- 대안: LLM이 성향과 상품을 직접 결정하는 방식은 설명 가능성·검증 가능성이 낮아 MVP에서 채택하지 않는다.

## ADR-009: MVP 인증은 메모리 토큰 저장소로 한정

- 결정: MVP 데모에서는 로그인 시 발급한 opaque token을 프로세스 메모리에 보관한다. 서버 재시작 시 토큰이 만료되며, 토큰 만료·로그아웃·다중 인스턴스 공유는 제공하지 않는다.
- 이유: 과제의 핵심은 진단 세로 슬라이스이고, 별도 인증 인프라 없이 사용자 소유권 검증을 보여주기 위함이다.
- 대안: 실제 서비스화 전에는 만료·폐기·재발급 정책과 공유 세션 저장소 또는 검증 가능한 토큰 체계를 도입한다.

## ADR-010: 등급 비교는 실제 적합성 판단이 아닌 내부 탐색 필터

- 결정: 5단계 성향과 1~6 카테고리 위험등급의 비교식은 과제용 예시 데이터를 탐색하기 위한 내부 규칙으로만 사용한다. 화면과 API에서는 `투자 권유 가능`, `적합성 판단` 대신 `탐색 기준`, `안내 범위`로 표현한다.
- 이유: 단순화한 비교식이 실제 금융기관의 상품별 위험정보·고객 정보·법적 절차를 대체하지 않으며, 사용자에게 투자 자문으로 오해될 수 있기 때문이다.
- 대안: 실제 서비스화 시 상품별 공식 위험정보, 투자자 정보 확인, 적합성·적정성·설명의무 등 별도 준법 설계와 검토를 거친다.

## ADR-011: P0 예시 상품은 카테고리 위험등급과 일치

- 결정: P0에서는 상품과 소속 카테고리의 `risk_grade`를 동일하게 유지하고, 시작 시 시드 데이터 불변식을 검증한다.
- 이유: 두 필드를 모두 노출하면서 서로 다른 등급을 허용하면 추천 필터와 상품 상세가 모순될 수 있다.
- 대안: P1에서 상품별 위험등급을 독립적으로 운영할 경우 카테고리 필터와 상품 필터의 우선순위·불일치 처리 규칙을 별도로 정의한다.
