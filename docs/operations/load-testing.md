# 단계별 부하테스트 계획

기준일: 2026-10-26. **아직 부하테스트를 실행하지 않았으며 아래 숫자는 제안 목표다.** 도구는 k6를 우선 제안한다. 일반 API 성능과 외부 LLM 호출 지연·비용은 별도로 측정한다.

| 시점 | 부하 | 핵심 경로 | 통과 목표(미측정) |
|---|---|---|---|
| 저장소 분리·DB 연결 | 1 VU smoke, 이후 10 VU 10분 | 용어 목록·상세, 개념·퀴즈, 로그인 후 학습 기록 | 조회 p95 <1초, 계산 p95 <2초, 예상 밖 오류 <1% |
| 과거 차트 복기 제공 | 30 VU 15분 | 과거 구간 조회, 답안 제출, 복기·진도 저장 | 같은 지연·오류 목표 + 데이터 미래 노출 0건·중복 저장 0건 |
| 성능 개선 실험 | 10→30→50 VU 단계 증가 | 읽기/쓰기 혼합, 서로 다른 사용자 | 병목·포화점·회복 시간을 기록; 처리량 개선 전후 비교 |

VU(가상 사용자 수)는 RPS와 다르다. 사용자 대기 시간을 둔 closed model인지 요청 도착률을 고정한 모델인지 결과에 명시한다. 조회·쓰기 비율은 최초 80:20을 가설로 두고 실제 사용 패턴이 생기면 갱신한다. 429 등 의도한 제한과 예상 밖 5xx·타임아웃을 분리한다. 차트 API와 모델 API는 아직 없으므로 해당 시나리오는 구현 후 추가한다.

## 실행 순서와 증거

1. 전용 staging DB·테스트 사용자·데이터 크기·API 이미지 SHA·DB migration 버전·배포 지역과 사양을 고정한다.
2. warm-up 후 본 측정을 분리한다. 애플리케이션 시작·무료 호스팅 절전 복귀 시간은 별도 지표로 남긴다.
3. API별 p50/p95/p99·RPS·오류율과 CPU·메모리·GC·Hikari active/pending·DB 연결/느린 SQL/잠금을 함께 기록한다. 필요한 계측은 후속 구현이다.
4. 느린 경로 한 개의 SQL·인덱스·N+1·payload·캐시를 확인해 하나씩 바꾸고 같은 조건으로 재측정한다.
5. 사용자별 인증 토큰으로 실행해 소유권을 확인한다. 조회 캐시가 사용자 간 데이터를 공유하지 않는지도 검사한다.
6. 원본 결과와 재현 명령·환경 설명을 infra의 결과 디렉터리 또는 CI artifact로 보관하고 docs에 링크한다. 모델 실험은 예측 정확도와 API 성능을 서로 다른 보고서로 남긴다.

동일 조건의 전후 결과가 있어야 성능 개선으로 판단한다. 목표를 달성했다고 기재하는 시점은 결과 artifact가 남은 뒤다. 부하테스트 스크립트와 관측 계측은 이번 디렉터리 정리 범위에서 구현하지 않았다.
