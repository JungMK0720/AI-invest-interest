# 16. 사용자 요구사항(UR) 분석

> 작성일: 2026-10-16
> 기준: 현재 구현(2차 고도화 반영) · 근거 문서 [12](12-product-strategy-and-user-journeys.md), [13](13-functional-nonfunctional-usecases.md), [15](15-requirements-problem-and-datamodel.md)
> 목적: "사용자가 무엇을 원하는가(UR)"를 기능·비기능 요구사항(FR/NFR), 화면, API, 테스트까지 끊김 없이 추적하고, 요구 대비 구현의 빈틈을 드러낸다.

---

## 1. 범위와 용어

| 용어 | 뜻 |
|---|---|
| **UR** (User Requirement) | 사용자의 말로 쓴 요구. "~하고 싶다" 형태로 쓰고, 구현 방법은 담지 않는다. |
| **FR / NFR** | UR을 시스템이 만족해야 할 기능·품질 조건으로 바꾼 것. 번호는 docs/13을 잇는다. |
| **수용 기준** | UR이 충족되었다고 판단할 관찰 가능한 조건. 가능한 한 자동 테스트로 고정한다. |

FinMATE는 금융상품을 추천하거나 주문하는 서비스가 아니라 **투자 성향을 근거와 함께 진단하고, 등급과 무관하게 상품 구조·용어를 배우고, 가정값으로 실험하는 학습 서비스**다. 이 경계(docs/13 §1) 밖의 요구는 UR로 기록하되 우선순위를 Won't로 둔다.

## 2. 분석 방법과 근거 수준

요구를 "누가 그렇게 말했는가"와 "그것이 얼마나 확인되었는가"로 나눠 기록한다. 확인되지 않은 것을 사실처럼 쓰지 않기 위해서다.

| 근거 수준 | 출처 | 예 |
|---|---|---|
| **E1 사용자 진술** | 프로토타입을 써 본 사용자의 제보(docs/12 §2) | "안정형으로 분류되니 원하는 상품을 공부할 수 없었다" |
| **E2 구현 관찰** | 코드·화면 점검, 통합 테스트, 실제 브라우저 사용 중 발견 | 진단 근거 스냅샷이 DB에 저장되지 않던 결함 |
| **E3 도메인 근거** | 금융소비자보호법·금융당국·거래소 공개 자료 | 적합성 원칙, 예금자보호 한도, 원문 개인정보 최소화 원칙 |
| **H 가설** | 제품 판단. 사용성 테스트로 검증해야 함 | "이름을 몰라도 질문으로 용어를 찾을 수 있으면 학습 이탈이 줄어든다" |

우선순위는 **MoSCoW**(Must/Should/Could/Won't), 사용자가 느끼는 가치는 **Kano**(Must-be 당연 / One-dimensional 성능 / Attractive 매력)로 함께 표시한다.

## 3. 이해관계자

| 이해관계자 | 관심사 | 영향 |
|---|---|---|
| 일반 사용자(금융 입문자) | 내 성향의 이유, 모르는 용어, 다음에 볼 것 | 주 사용자 |
| 진단 제한 사용자 | 등급과 무관한 학습, 다음 진단 시점 | 주 사용자 |
| 콘텐츠 운영자·검수자 | 용어 수정·게시, 이력, 출처 관리 | 보조 사용자 |
| 서비스 운영(개발자) | 재현성, 장애 시 폴백, 모델 회귀 방지 | 시스템 품질 |
| 금융 규제 맥락 | 투자 권유·자문으로 오인되지 않는 표현, 개인정보 최소화 | 제약 조건 |

## 7. 우선순위 해석

- **Must-be(당연)** 요구(UR-01·02·04·05·13·15)는 충족해도 칭찬받지 못하지만 빠지면 신뢰를 잃는다. 금융 서비스에서 "근거·재현성·원문 미저장·AI의 월권 금지"가 여기에 속한다. 그래서 이 요구들은 화면이 아니라 **테스트로 고정**했다.
- **One-dimensional(성능)** 요구(UR-07·09·10·12)는 품질이 좋아질수록 만족이 비례한다. 용어 수·검색 정확도·복습 간격처럼 숫자로 개선을 보여 줄 수 있게 지표를 남겼다.
- **Attractive(매력)** 요구(UR-03·08·11)는 없어도 불만은 없지만 있으면 차별점이 된다. FinMATE에서 AI가 의미 있는 곳이 바로 이 영역이다. 단, 매력 요구가 당연 요구(UR-04·05)를 침해하지 않도록 "등급 불변·원문 미저장"을 먼저 설계했다.

## 8. 갭 분석 — 요구 대비 기존 구현의 빈틈과 조치

2차 고도화 전 구현을 위 UR로 점검해 다음 빈틈을 찾았다. 모두 E2(구현 관찰) 근거다.

| # | 빈틈 | 영향받은 UR | 원인 | 조치 |
|---|---|---|---|---|
| 1 | 진단 근거 스냅샷이 **DB에 저장되지 않음** — 결과·이력의 evidence가 항상 null | UR-01·02 | 식별자를 직접 부여한 엔터티를 `save()`하면 merge로 사본이 반환되는데, 반환값을 버리고 원본에 스냅샷을 기록 | 반환된 관리 인스턴스를 쓰도록 수정, 통합 테스트로 고정 |
| 2 | 자유 서술 모델이 **40문장으로 학습**되어 새 표현에 약함(보류 115문장 정확도 0.52) | UR-03·12 | 학습 데이터 부족 | 설문 축 문장 조각 생성기 + 사람이 쓴 보류셋 분리 평가, 로지스틱 회귀로 교체(0.617, ±1등급 0.904) |
| 3 | 관리자가 용어를 고쳐도 **검색 인덱스에 반영되지 않음** | UR-16 | 문서 벡터를 배포 시점 JSON으로 만듦 | 문서 벡터를 DB 공개 용어로 만들고 게시 이벤트(커밋 후)로 재구성 |
| 4 | 자유 서술 비교가 **진단 기록에 남지 않음** | UR-03·11 | 결과 화면에서 따로 호출하고 버림 | 진단 제출에 선택 입력으로 통합, 추정 결과만 스냅샷 저장 |
| 5 | 용어 퀴즈 "새 문제"가 **항상 같은 문제** | UR-07 | 클라이언트가 seed를 보내지 않아 서버가 0으로 고정 | 요청마다 seed 생성 |
| 6 | 학습 화면이 **로그인을 요구** — docs/09 "학습은 열려 있어야 한다"와 모순 | UR-06 | 라우터 보호 설정 | 학습·용어·모의투자·모델 실험실 공개, 로그인 후 원래 화면 복귀 |
| 7 | 주제와 무관한 잡담에도 **성향을 추정** | UR-12 | 보류 기준을 투자 서술로만 맞춤 | 주제 무관 문장 30개로 보류 규칙 재조정(별도 20개에서 100% 보류) |
| 8 | 진단 선택지에 **접근성 이름 없음** | UR-14 | `role="radio"` 버튼에 이름 미지정 | `aria-label`, `radiogroup` 추가 |
| 9 | 관리자가 **새 용어를 만들거나 공개를 내릴 수 없음**, 이력 없음 | UR-15·17 | 편집·게시만 구현 | 생성·공개 내리기·초안 버리기·불변 이력·운영 현황 추가 |

## 9. 검증 계획 (실사용자 대상, 미실시)

자동 테스트는 "시스템이 약속대로 동작하는가"를 보장하지만 "사용자에게 도움이 되는가"는 보장하지 않는다. 출시 전 5~8명 과업 기반 사용성 테스트를 다음처럼 계획한다.

| 과업 | 관련 UR | 성공 기준 | 측정 |
|---|---|---|---|
| T1. 진단 후 "왜 이 성향인지" 자기 말로 설명하기 | UR-01 | 근거 답변 2개 이상 언급 | 사후 인터뷰 |
| T2. "배당락"을 모르는 상태에서 뜻과 매수 기한 찾기 | UR-07·08 | 3분 안에 정답 | 과업 시간·성공률 |
| T3. 이름을 모르는 개념("빌린 돈을 못 갚으면 주식이 팔리는 것") 찾기 | UR-08 | 2회 검색 안에 반대매매 도달 | 검색 횟수 |
| T4. 안정형으로 진단된 뒤 레버리지 ETF의 변동성 손실 설명하기 | UR-06·09 | 시뮬레이션 결과를 근거로 설명 | 설명 정확도 |
| T5. 틀린 문제를 다음 날 다시 풀기 | UR-10·11 | 내 학습에서 1분 안에 도달 | 이동 경로 |
| T6. 모델 실험실에서 "이 모델을 어디까지 믿을지" 말하기 | UR-12 | 한계 1개 이상 언급 | 사후 인터뷰 |

정량 지표: 과업 성공률, SUS 점수, 자유 서술 입력률(UR-03 수요 확인), 학습 경로 클릭률(UR-11), 복습 재방문율(UR-10). 자유 서술 모델은 **동의를 받은 실제 문장**으로 재평가하기 전까지 보조 신호로만 쓴다.

## 10. 한계

- E1 근거는 소수의 제보이며 모집단 조사가 아니다. 페르소나는 이를 바탕으로 한 가설이다.
- 성향 신호 모델의 평가 문장은 한 사람이 썼고, 학습 문장 대부분은 생성 문장이다(docs/18).
- UR-18(실데이터)은 데이터 이용 계약과 라이선스가 필요해 설계까지만 진행했다.
- 진단 월 1회 제한은 FinMATE 자체 정책이며 금융권 공통 규정이 아니다(docs/09).
