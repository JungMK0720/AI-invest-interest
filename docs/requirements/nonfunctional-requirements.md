# 비기능 요구사항 (NFR)

기준일: 2026-10-26. **수치는 제안 목표이며 현재 측정한 성능이나 보장 수치가 아니다.** 운영 규모·비용·배포 환경을 확인한 뒤 승인·조정한다. 실제 충족 여부는 실행 환경·커밋·부하 설정·결과를 함께 기록한 증거로 판정한다.

## 기존 품질 요구

ID와 요구 정의는 [기존 FR/NFR 원본](../reference/13-functional-nonfunctional-usecases.md)에서 보존했다. 이전 테스트 언급은 과거 기록이며 이번 정리의 새 실행 증거로 간주하지 않는다.

| ID | 품질 속성 | 요구사항 | 검증 방법 |
|---|---|---|---|
| NFR-01 | 보안·권한 | 보호 API는 인증 토큰을 요구하고, 사용자는 자신의 진단·진도만 조회한다. 관리자 기능은 역할로 분리한다. | 권한 테스트, API 통합 테스트 |
| NFR-02 | 결과 재현성 | 같은 콘텐츠 버전·계산식 버전·입력·seed는 같은 결과를 만든다. 결과에는 사용 버전을 저장한다. | 동일 요청 반복 비교 |
| NFR-03 | 안전한 표현 | 모든 결과에 교육 목적·가정·기준 시각·한계를 표시하며, 추천·수익 보장·주문으로 오해될 문구를 차단한다. | 금칙어·스냅샷 UI 검수 |
| NFR-04 | 데이터 정확성 | 숫자 범위·단위·통화·기간을 서버에서 검증한다. 출처 없는 학습 카드와 만료된 데이터는 게시할 수 없다. | JSON/DB 제약, 콘텐츠 기동 검증 |
| NFR-05 | 데이터 추적성 | 실데이터는 공급자, 원문 URL, 수집 시각, 기준일, 지연, hash, 변환 버전을 함께 기록한다. | 스냅샷·감사 로그 점검 |
| NFR-06 | 성능 | 일반 조회 API p95 1초 이내, 교육용 계산 API p95 2초 이내를 목표로 한다. 외부 공급자·AI 지연은 별도 표시한다. | 부하 테스트(검증 필요) |
| NFR-07 | 가용성·복구 | AI·외부 데이터가 실패해도 진단 결과와 마지막 승인 스냅샷은 조회되며, 템플릿·캐시·재시도 경로를 제공한다. | 장애 주입 테스트 |
| NFR-08 | 멱등성·중복 방지 | 같은 제출 idempotency key는 중복 진단·퀴즈 시도·수집 작업을 만들지 않는다. | 재전송 테스트 |
| NFR-09 | 개인정보 최소화 | 답변 원문·토큰·프롬프트·민감 로그를 일반 로그에 남기지 않고 보존·삭제 정책을 둔다. | 로그 샘플·보존 정책 점검 |
| NFR-10 | 관측 가능성 | 요청 ID, 계산식 버전, 오류 코드, 외부 호출 지연, 데이터 신선도를 구조화 로그와 지표로 남긴다. | 대시보드·알람 점검 |
| NFR-11 | 접근성·반응형 | 키보드 탐색, 명확한 오류 문구, 색상 외 상태 표현, 모바일 폭의 학습 카드·그래프를 지원한다. | WCAG 체크리스트·브라우저 점검 |
| NFR-12 | 유지보수성 | 개념·문항·상품·시나리오는 버전된 콘텐츠로 분리하고, API·화면·계산식 변경은 추적 문서와 함께 갱신한다. | 스키마 검증·코드 리뷰 |
| NFR-13 | 테스트 가능성 | 규칙 판정, 퀴즈 채점, 시뮬레이션 계산, 권한, 폴백을 자동 테스트하고 발표 범위 빌드를 재현한다. | `mvn test`, `npm run build`, 계약 테스트 |
| NFR-14 | 저작권·출처 | 그림·원문·공시를 사용할 때 사용 조건과 출처를 저장하고, 재배포 불가 자료는 링크·요약으로 대체한다. | 콘텐츠 검수 체크리스트 |

|---|---|---|---|---|
| NFR-15 | 학습 내용 정확성 | 정의·사례에 공식 출처·확인일·콘텐츠 버전을 남기고 제도 수치와 가정값을 구분한다. 기관 분류를 일률적인 위험 순위로 표현하지 않는다 | 콘텐츠 검수, 출처·확인일 필수 검사, 개념 전후 설명 과업 | 계획 |
| NFR-16 | 미래 정보 누수 방지 | 리플레이 데이터와 특징은 의사결정 시각 당시 이용 가능해야 한다. 이후 가격·사후 수정 지표·미공개 공시·전체 기간 정규화 결과를 노출하지 않는다 | 시점 경계/공개 지연 테스트, 응답·네트워크 payload 검사, 데이터 생성 과정 감사 | 계획 |

## 단계별 부하 테스트 제안

공통 조건: 개발/스테이징의 **측정 전 목표**다. AI 외부 호출은 별도 계측하고 일반 조회와 섞지 않는다. 가상 사용자 수는 실제 DAU나 지원 가능 사용자를 뜻하지 않는다. 데이터 크기·인덱스·컨테이너 자원·DB 요금제·연결 수·캐시 상태를 함께 고정한다.

| 단계 | 제안 부하·시간 | 제안 통과 기준 | 목적 |
|---|---|---|---|
| 0. 기능 확인 | 1 가상 사용자, 3분 | 예상 4xx 제외 오류 0, 세션/권한/헬스 확인 | 측정 도구와 시나리오 유효성 확인 |
| 1. 첫 학습 배포 | 10 가상 사용자, 10분 | 일반 조회 p95 ≤1초, 가정값 계산 p95 ≤2초, 예상하지 않은 5xx·timeout <1% | 기존 NFR-06을 작은 규모부터 검증 |
| 2. 리플레이 추가 | 30 가상 사용자, 15분 | 다음 구간 공개 API p95 ≤1초, 오류 <1%, 미래 데이터 노출 0, 중복 결정 0 | 공개 경계와 상태 일관성 확인 |
| 3. 운영 전 용량 탐색 | 10→30→50 가상 사용자, 단계별 5분 | 최초 목표 초과 시 지점·DB 대기·CPU·메모리 기록, 자동 증설 전 비용 확인 | 감당 가능한 운영 범위 결정 |
| 4. 회복 | 단계 1 부하 5분 후 외부 AI 지연/실패 주입 | 규칙 결과와 학습 조회 유지, 템플릿 폴백 동작, 토큰·자유서술 로그 노출 0 | 장애 시 핵심 경로 확인 |

첫 연결 풀은 API 인스턴스당 작게 시작하고 서버 수×풀 크기가 DB 허용 연결 예산을 넘지 않게 한다. 구체 값은 [DB 전략](../architecture/database-strategy.md)에서 정하며, 부하 결과 없이 인스턴스나 풀만 늘리지 않는다. 부하 도구·스크립트는 후속 작업이며 아직 추가하거나 실행하지 않았다.
